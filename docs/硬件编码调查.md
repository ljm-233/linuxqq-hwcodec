# QQ 屏幕共享硬件编码调查（Linux PC 版，2026-10-03）

## 结论

**PC 版 QQ 有 NVENC 实现，但用户侧没有任何入口能让它走硬编。**

现在实际在编码的是 `libAVSDKPlugin.so` 自带的**软件**编码器（OpenH264 量级：实测 2560×1600
下每秒只编得动约 6 帧）。配置、环境变量、COM 入口、符号介入四条路都试过，全部到不了那个
判断点；要真硬编只能等**腾讯在 Electron 侧给出开关**，或者换客户端。

## 环境

| 项 | 值 |
|---|---|
| 系统 / 合成器 | Arch Linux + niri（Wayland） |
| QQ | 3.2.34-53644（`/opt/QQ`） |
| 客户端修复 | `linuxqq-wayland-fix` 0.2.13-1 |
| GPU | NVIDIA RTX 5060（`renderD129`）+ Intel i915（`renderD128`） |
| NVIDIA 驱动 | nvidia-utils 615.71.09 |

## 证据链（每条都可复现）

### 1. NVENC 实现存在

```bash
ls /opt/QQ/resources/app/avsdk/            # broadcast-core.so 470 KB、libAVSDKPlugin.so 33 MB …
B=/opt/QQ/resources/app/avsdk/broadcast-core.so
strings -a $B | grep -iE 'NvEncoder|NvEncodeAPI|cuvid|AmfEncoder|OpenH264Encoder' | head
strings -a $B | grep -i 'NvEncoder.c'      # …/broadcast-core/broadcast-core/linux/NvEncoder.c
```

`broadcast-core.so` 内含 `NvEncoder_Create/InitEncConfig/DoEncode`、`NvEncodeAPICreateInstance`、
`NvEncodeAPIGetMaxSupportedVersion`、NVDEC（`cuvidCreateDecoder`）、AMD `AmfEncoder`、
软件兜底 `OpenH264Encoder_*`；它会 `dlopen` `libnvidia-encode.so`、`libcuda.so`、`libnvcuvid.so`
（另有 `libmfx.so.1`=Intel QSV、`libamfrt64.so.1`=AMD）。

### 2. 缺的不是库

```bash
ldconfig -p | grep -E 'libnvidia-encode|libcuda\.so|libnvcuvid'   # 三个都在
ldconfig -p | grep -E 'libmfx|libamfrt64'                          # 这两个缺（QSV/AMF 因此不通）
```

实测对这些**无版本号**名字的 `dlopen` 全部成功 —— 所以"名字不对/库缺失"不是原因。

### 3. COM 入口从未被调用（决定性）

```bash
B=/opt/QQ/resources/app/avsdk/broadcast-core.so
nm -D --defined-only $B                     # 只有 3 个：DllGetClassObject@@VERS_1.0 / DllCanUnloadNow / RegisterLog
for f in $(find /opt/QQ -name '*.so'); do
  nm -D --undefined-only "$f" 2>/dev/null | grep -q DllGetClassObject && echo "引用者: $f"
done                                        # 无输出 → 没有任何库引用它
```

探针实测（共享进行中，探针在收帧进程里）：

```
dlopen 40 次（失败 1）；dlsym 0 次；dlvsym 77 次；DllGetClassObject 0 次
dlopen 命中目标："libAVSDKPlugin.so" -> 成功
dlopen 命中目标："broadcast-core.so"  -> 成功
```

即：broadcast-core 是运行时被 `dlopen("broadcast-core.so")`（裸名字）加载的，**但它的 COM
入口一次都没被调用** —— 那条路根本没走，谈不上"我们没拦到"。

### 4. 按名字 hook 不行

`BroadcastCore_EnumEncoderDevice`、`IsSupportedHardware`、`SwitchEncoderDevice`、`SetEncoder`、
`SetCodecId` 这些名字**只存在于字符串表**（是 COM 接口的方法名），不是导出符号。

### 5. 编码器在 `libAVSDKPlugin.so`，而它锁死了自己的调用点

```bash
A=/opt/QQ/resources/app/avsdk/libAVSDKPlugin.so
nm -D $A | wc -l                            # 7961 个导出符号
nm -D $A | grep -iE 'CreateH264Encoder|O264rtCreateSVCEncoder' | head
strings -a $A | grep -E 'CVideoEncoder::Init|ReadyEncode' | head
readelf -d $A | grep -E 'FLAGS|NEEDED'      # FLAGS: SYMBOLIC ← 内部调用绑定自己
```

它自带整份 FFmpeg H.264 与运行期日志串 `CVideoEncoder::Init … hardware: %d`、
`ReadyEncode … use_hardware[%d]`；因为带 `SYMBOLIC`，**对它的导出函数做 `LD_PRELOAD` 介入
拦不到库内部的调用点**。

### 6. SDK 自带的"测试配置文件"实测无效（最后一搏）

字符串承诺的开关：

| 文件 | 键 | 命中时的日志 |
|---|---|---|
| `aMavEngineConfig.txt` | `uiUseHw`、`uiUseHWAccelerate` | `aMavEngineConfig.txt: uiUseHw[%d->%d]` |
| `aConfig.txt` | `dwUseHWAccelerate`、`HwEnc` | `be careful local has test config file aConfig.txt: dwUseHWAccelerate[%d->%d]` |

```bash
# 文件名是相对的 → 放进 QQ 的进程工作目录
readlink /proc/$(pgrep -x qq | head -1)/cwd          # → /home/link

printf 'uiUseHw=1\nuiUseHWAccelerate=1\n'      > /home/link/aMavEngineConfig.txt
printf 'HwEnc = 1\ndwUseHWAccelerate = 1\n'    > /home/link/aConfig.txt

# 完全退出 QQ（含托盘）→ 从修复版启动器重启 → 开一次共享 → 查日志
ps -o lstart= -p $(pgrep -x qq | head -1)            # 确认启动时间晚于文件 mtime
grep -aiE 'HwEnc|uiUseHw|UseHWAccelerate|hardware:|use_hardware' \
     /run/user/1000/linuxqq-wayland-fix.log | tail
```

**结果：没有任何输出** —— 既没有 `[0->1]`，也没有"加载失败/解析失败"的任何提示。

判定：这段代码在 PC 版里很可能未启用。旁证是库里那条配置路径写的是 Android 的绝对路径
`/sdcard/Android/data/com.tencent.mobileqq/aMavEngineConfig.txt`（该库是手机端共用的）。

### 7. 结论

要有硬编，需要**腾讯在 Electron 侧**调用它自己的
`BroadcastCore_IsSupportedHardware` / `SwitchEncoderDevice`（或提供真正的用户开关）；
用户侧的配置、环境变量、符号介入三条路都到不了那个判断点。

## 探针怎么用（本项目的主要产物）

```bash
cd ~/coding/linuxqq-hwcodec && ./build.sh          # 必须看到 4 个 wrapper + 3 个目标符号 ✓

pgrep -x qq                                        # 必须为空！QQ 单实例，不退出必白跑

HWPROBE_VTABLE=1 ./linuxqq-hwcodec-probe           # 用探针启动 QQ
# 开一次共享，共享进行中：
./linuxqq-hwcodec-probe --selfcheck-once           # 要看到「自检结论：可以采集 … 共享=进行中」
cat ~/.cache/linuxqq-hwcodec/probe-*.log
```

日志里能回答的问题：

| 想看什么 | 看哪一行 |
|---|---|
| 探针有没有进收帧进程 | `自检结论：可以采集 —— 探针=在 修复库=在 broadcast-core=在 共享=进行中` |
| 谁加载了 broadcast-core | `dlopen 命中目标："broadcast-core.so" -> 成功` |
| 它取过哪些符号 | `dlsym/dlvsym 查找名 top8（共 N 种）：…` |
| COM 接口有没有被调用 | `已代理 IClassFactory`、`vtable[槽位] call/ret`、`符号介入路径：…` |
| 编码库加载情况 | `后端加载情况：NVENC=… CUDA=… OpenH264(软编)=…` |

## 走过的弯路（现在都有回归测试覆盖）

| 坑 | 现象 | 教训 |
|---|---|---|
| 探针没进 ppapi | `自检：没有收帧进程` / `探针不在收帧进程` | QQ 单实例：**必须先完全退出再启动**；ppapi 是主进程 `fork` 出来的 |
| 日志 fd 被关 | 探针在、broadcast-core 在，却一行不写 | Chromium fork 后关掉不认识的 fd → 写日志前 `fcntl(F_GETFD)` 校验并重开 |
| `DllGetClassObject` 没导出 | 直接链接的调用方绕过我们（后来证明根本没人调） | `LD_PRELOAD` 介入要求**导出同名动态符号** |
| `RTLD_DEFAULT` 兜底 | 解析回自己 → 无限递归 → 栈溢出（rc=139） | 真实实现只走 `RTLD_NEXT`，且结果等于自己就作废 |
| `dlvsym` 第一版 | 返回 nil → 破坏 glibc 版本探测（`dlvsym(...,"dlopen","GLIBC_2.34")` 也 nil） | 只能**纯透传**；引导期扫 ELF dynsym（现代 glibc 只有 `DT_GNU_HASH`） |
| `alarm()` 做周期摘要 | 每个被注入进程 20 秒后 SIGALRM → **打死宿主**（142） | 注入类工具**不要用信号/定时器**；改成在已有调用路径上惰性判断 |
