# 让 QQ 跑在 N 卡上：七种尝试与最终结论

**结论：本机用户侧无法实现。** 七个配置全部实测失败（2026-10-03）。下面是每条的死因、根因，
以及**可复现的命令与判据**，避免以后重试一遍。

## 环境

| 项 | 值 |
|---|---|
| 合成器 | niri（Wayland，原生） |
| 核显 | Intel Arrow Lake，`card1` / `renderD128`（niri 自己渲染在这上面） |
| 独显 | NVIDIA RTX 5060 Laptop，`card0` / `renderD129`，驱动 615.71.09（open 模块） |
| 客户端 | QQ 3.2.34 + `linuxqq-wayland-fix`（Wayland 门户补丁） |
| 核显侧驱动 | Mesa（ANGLE-Vulkan → Intel Vulkan；GL → llvmpipe 软件渲染） |

## 判据（三条，权重不同；2026-10-03 修正过一次）

1. **【决定性】收帧进程 `ppapi` 里 `llvmpipe` 线程数 = 0** —— 还有 llvmpipe 线程就是在用 CPU 软件
   渲染，与哪块 GPU 无关；这条不过，其它数字都不作数。
2. **【辅助】`ppapi` 打开 `renderD129`** —— **同时持有 i915 fd 本身不算失败**（可能是
   `drm-total-system0: 0` 的闲置 fd）；`verdict` 会打出它 i915 客户端的**实际分配**，>0 才说明真在用。
3. **【辅助】归因到 qq 的显存增长** —— `mark` 记两个基线（全卡 + 归因 qq），共享中 `verdict` 看差值。

> ⚠️ **判据修正记录（两处真错误，2026-10-03 由用户质疑后查出）**
> - 旧 `verdict` 用 `nvidia-smi --query-compute-apps` 数 qq 进程 —— 那个接口**只列计算进程**，
>   QQ 是图形客户端、**永远不会出现**，输出恒为 0，却被当成"没上 N 卡"的论据 ✗。现改为解析
>   `nvidia-smi` 默认输出的 **Processes 表**（含 Graphics/Compute），按 pid 匹配；读不到就明确打
>   「无法读取」，不输出 0 冒充结论。
> - 旧判据 3 用 `memory.used` 的**整卡**差值 → 浏览器/合成器的变化也算进去，`+712 MiB`（QQ 启动分配）
>   与 `+167 MiB`（别的子进程）被误当成收益 ✗。现保留整卡数但标注「未归因、仅供参照、不作判据」，
>   真正看的是**归因到 qq** 的差值。
>
> **复核结果：七个配置"全部失败"的结论不变，依据换成有效证据** —— `prime-1`、`bwrap-hide-igpu`、
> `xwayland-bwrap` 三次实测中**共享期间 ppapi 内有 18 个 llvmpipe 线程**（判据 1，决定性）。

> ⚠️ 只满足第 2 条**不算** —— `prime-1` 时节点开了但 llvmpipe 有 18 线程；
> 只看"整卡显存涨了"也不算 —— `bwrap-hide-igpu` 那次 +712 MiB 是**启动分配**，按基线重测是 **-27 MiB** ✗。

## 七个配置的实测结果（全部 ✗）

| 配置 | 做法 | 死因 |
|---|---|---|
| `baseline` | 不改（核显 + llvmpipe + `ANGLE=off`） | 本来就在核显 |
| `angle-gl-nvidia` | `QQ_WAYLAND_FIX_ANGLE=off` + `--use-gl=angle --use-angle=gl` | **GLX 需要 X11**，QQ 是原生 Wayland → ANGLE 回退到 Mesa |
| `prime-1` | `DRI_PRIME=1` | Mesa 收下变量、节点也开了，但**实际仍走 llvmpipe**（18 线程、VRAM 32 MiB） |
| `vulkan-nvidia` | 锁 NVIDIA Vulkan ICD + `--use-angle=vulkan` | **ANGLE 仍挑 Intel 的 Vulkan**；`nvidia-smi` 里 qq 进程数 = 0；且画面变小 |
| `xwayland-nvidia` | `--ozone-platform=x11`（XWayland） | ppapi 仍 `renderD128`；VRAM +356 MiB **涨在别的 qq 子进程**（假阳性案例） |
| `bwrap-hide-igpu` | `bwrap --dev-bind / / --tmpfs /dev/dri --dev-bind …/renderD129 …` | 命名空间里**只剩 N 卡**（已实测：`renderD128` 报"没有那个文件"），但它**宁可 llvmpipe 软件渲染也不上 N 卡**（VRAM 相对基线 -27 MiB） |
| `xwayland-bwrap` | 上面两条叠加（最后一击） | 同上：ppapi 仍走核显/软件路径（**共享期间 18 个 llvmpipe 线程**，判据 1 未过）。注：当时引用的「VRAM +167 MiB」未归因、「`nvidia-smi` 里 qq = 0」是无效指标，均已剔除 |

补充：`bwrap` 方案里 ppapi 确实会持有一个 i915 的 fd，但它是**闲置的**
（`drm-total-system0: 0`，一个字节都没分配）—— 所以"存在 i915 fd"本身不能作为失败判据，
要看**归因到 qq 的显存增量**和**ppapi 的 llvmpipe 线程数**（后者是决定性的）。

## 根因

这套环境下**客户端拿不到可用的 NVIDIA GL/EGL**：

- NVIDIA **EGL 在 Wayland 平台 `eglInitialize` 失败**（上个会话实测，`eglinfo` 可复现；Mesa 在同一平台成功）
- **GLX 只在 X11 可用** → 原生 Wayland 下没有 GLX
- Mesa 的 `DRI_PRIME` offload 走到 **llvmpipe**（软件渲染）
- 强制 `VK_ICD_FILENAMES` 到 NVIDIA **对 ANGLE 的设备选择无效**（仍挑 Intel）
- `nvidia_drm.modeset=Y`、`libnvidia-egl-wayland2.so`、GBM、各 platform JSON **都在位** —— 所以**不是内核参数或缺库的问题** ✗

属于「NVIDIA 驱动 + Electron/ANGLE + 混合显卡 + Wayland」的交互问题，**用户侧无解**。
换 Mesa 的 NVK（nouveau）理论上可行，但要替换整个 NVIDIA 驱动栈，不建议。

## 已经解决的部分（这些是真的）

- **不冻机**：`saver` 档（15fps + 960×600）+ 内存刹车 → 共享期间 `Shmem` 稳定（0~1 MB/s），**多次实测**
- **画面正常**：`QQ_WAYLAND_FIX_ANGLE=off` 修掉了"接收视频画面缩成小图"
- 当前可用状态 = `baseline`（核显 + llvmpipe + ANGLE off），共享可用、内存不涨
- 硬件**编码**同样换不了：编码器在腾讯自己的 `libAVSDKPlugin.so` 里（软编），无开关、无环境变量、
  COM 入口不被调用、符号被 `SYMBOLIC` 锁死 —— 见 `docs/硬件编码调查.md`
