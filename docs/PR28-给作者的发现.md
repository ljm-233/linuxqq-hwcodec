# PR #28 实测发现（给作者）

> 本文是外部实测记录，**未向上游发送任何内容**。相关过程文档：`docs/PR28-NVENC-试跑.md`、`docs/硬件编码调查.md`。
> 被测对象：`SHORiN-KiWATA/linuxqq-wayland-fix` PR #28「screenshare: 可选改用 NVENC 编 H.264」（作者 FJKiXfaR，分支 `feat/nvenc-screencast`，`b0657a8`）。

## 结论

**这个 PR 的接管是成功的，而且顺带解决了长期存在的内存堆积问题** ✓ —— 本机实测：NVENC 生效时全分辨率共享 **`Shmem` 稳定 0 MB/s**，而未启用时同档位客户端 i915 GEM 以 **398 MB/s** 增长（根源是软编每秒只编得动约 6 帧，余下的帧全被留住）。

**唯一剩下的问题是：对端收不到画面（QQ 转圈）** ✗。我们已经逐个排除：几何、packet 字段偏移、回调时序、码流封装、profile、关键帧/参数集 —— 编码侧输出已确认正确（`SPS=有 PPS=有 IDR=有`）却仍不出画面，因此故障点应在**钩子与 QQ 下游的交接契约**（第四节）。

## 一、做到了什么

- NVENC 确实接管：`qq --type=ppapi` 进程映射 `libnvidia-encode`（5 段）/`libcuda`（6 段）；日志 `NVENC: 会话就绪 …` → `出流 …` → `出帧 idx=… P … 字节` → `回调已返回`
- 多路对象各自正常：`1200x1920@23 660kbps`、`1920x1200@23 660kbps`、`1920x1200@23 2700kbps`、`2560x1600@23 3200kbps`
- **内存收益**：全分辨率 2560×1600 + 60fps 共享下 `Shmem` 稳定 0 MB/s（同档位无 NVENC 时 398 MB/s）

## 二、问题：对端始终转圈 —— 已排除项与证据

| # | 假设 | 结论 | 证据（本机实测） |
|---|---|---|---|
| 1 | 会话几何读反 | ✗ 排除 | 会话几何取自帧头 `+0x00`/`+0x04`；用 **Y 平面行距**(`+0x18`) 交叉验证：`开始编码 1920x1200 ypitch=1920 uvpitch=960` → `ypitch == 宽` → 帧本来就是横的。那个 `1200x1920` 的对象经同一判据确认是**真竖屏**（很可能是给手机端的另一路） |
| 2 | packet 字段偏移 | ✗ 排除 | 旁观模式（`QQ_NVENC=1`）下原实现回调给出 `-> data=0x11ec02204040 len=86308 idx=0`，连续三帧 `data` **同一地址**（原实现复用同一缓冲）、`len` 合理、`idx` 递增 → 填的 `+0x08/+0x10/+0x14/+0x18` 与契约一致 |
| 3 | 回调时序 | ✗ 排除 | 把回调推迟到「下一次 `DoEncode` 进入时补发」（影子 packet + 码流 memcpy 副本，规避 `nvEncUnlockBitstream` 后缓冲失效）——**同样转圈** |
| 4 | 码流封装 | ✗ 排除 | 原实现与 NVENC 路径**都是 Annex-B（4 字节起始码）** |
| 5 | profile | ✗ 排除 | 默认（High `0x64`）与强制 **Baseline**（`0x42` + CAVLC + 清 VUI + 去 AUD）**都转圈** |
| 6 | 缺关键帧/参数集 | **已修好，但仍不出画面** | 首帧 `req_flags=0x6 pictureType=3 is_idr=1 参数集=33`；`封装=Annex-B SPS=有 PPS=有 IDR=有`；对端依旧转圈 |

## 三、过程中的驱动/API 行为（对作者有直接价值）

1. **驱动不守约**：请求 `NV_ENC_PIC_FLAG_FORCEIDR`（`req_flags` 含 `0x2`）后，返回的 `pictureType` 仍为 `0`（非 IDR），且不输出参数集。
   → 需要**自己管 IDR 周期**（首帧 + 每 N 帧请求），并在"请求了仍不给"时**重开会话**（新会话确实会带 SPS/PPS + 关键帧）。
2. **`nvEncGetSequenceParams` 在 `nvEncInitializeEncoder` 之后立刻调用取不到**（驱动要等第一帧）。
   → 需要**编码后重试**，或**直接从码流里抠 SPS(7)/PPS(8)** 缓存；拿到参数集后**下一帧立刻强制 IDR**，让接收端第一次就收到完整起点。
3. 原始实现的**回调是异步的**，且递出的是**它自己的 packet 对象**（旁观 dump 里 `DoEncode` 返回时 packet 尚未填完，不能据此判断偏移）。

## 四、剩下的头号嫌疑：钩子与 QQ 下游的交接契约

编码侧参数已全部正确（关键帧、参数集、几何、封装、profile 都验过），但下游接收不到可解画面。建议从这几处插桩：

1. 除 `+0x08/+0x10/+0x14/+0x18` 外，**是否还有下游必需的字段**（时间戳、序号、关键帧标志、多路对象的各自标识）？
2. 下游是否要求**回调发生在 `DoEncode` 返回之后**，或**在特定线程**上回调？
3. 建议在 `fEncoderDoneCallback` 前后与下游消费点**对比原实现与 NVENC 路径的 packet 内容与调用上下文**（原实现那侧可以复用本仓库 `QQ_NVENC_HEXDUMP=1` 的打法）。

## 五、本地实验补丁（可直接取用，**未提交上游**）

`patches/` 目录（均基于 `pr28`，只在 worktree 内应用）：

| 文件 | 内容 |
|---|---|
| `pr28-asynccb.patch` | `QQ_NVENC_ASYNCCB=1`：回调推迟到下一次 `DoEncode` 进入时补发（影子 packet + 码流副本） |
| `pr28-fixkey.patch` / `pr28-fixkey-idr-sps.patch` | `QQ_NVENC_FIXKEY=1`：自管 IDR 周期 + 缓存并逐帧补 SPS/PPS；`QQ_NVENC_REOPEN_IDR=1`：驱动不给 IDR 就重开会话 |
| `pr28-geom-fix.patch` | `QQ_NVENC_GEOM_FIX=1`：按 Y 平面行距判断宽高是否读反（本机判定为"未读反"，故未启用） |
| `pr28-local-experiments.patch` | 以上合并后的累计补丁 |

**构建**（只需构建期头文件 `ffnvcodec/nvEncodeAPI.h`，CUDA 是运行时 `dlopen`）：

```bash
git worktree add /tmp/pr28-build pr28          # 不要动主 clone
make NVENC_INC=<nv-codec-headers>/include libqq-nvenc.so
```

Arch 的依赖是 AUR 的 `nv-codec-headers`（Debian 为 `libffmpeg-nvenc-dev`）。

**诊断开关**（本仓库）：`nvenc-status.sh`（一条命令给结论）、`QQ_NVENC_HEXDUMP=1`（两条路径的码流首部 + NAL 解析 + `req_flags/pictureType/is_idr`）、`try-gpu-config.sh`（GPU 归属核查）。
